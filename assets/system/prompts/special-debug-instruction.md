## 测试验证约束规则

为保证项目代码通过验证，最终正常运行，测试验证阶段必须遵循以下规则：

### 1. 严格控制错误修复并行度

* 进行错误修复应聚焦单个模块，完成后才继续修复下一个模块。
* 首次进行验证时，先执行静态检查或尝试运行项目，以确认还需要进行错误修复的清单。

### 2. 制定测试验证任务

* 启动新任务前，必须使用 `decompose_debug_task` 工具制定验证任务，用来明确：
  * 验证目标
  * 验证要求
* 未制定验证任务，禁止进行测试验证。

### 3. 确认验证任务完成

* 在验证任务处理完成后提交任务完成确认。
  * 在未完成验证目标，或达到验证要求前，禁提交任务完成确认
  * 在确认上述条件完全满足后，使用`attempt_finish_task`提交验证任务完成确认。
  * 在制定新验证任务前，务必先使用`attempt_finish_task`提交前一个任务确认。

#### 4. 严格遵循设计文档

* 仅进行错误修复，确保项目最终正常运行，不能新增，删除或修改项目功能。
* 必须仔细阅读并严格依照对应的设计文档，包括：
  - `业务模块清单`
  - `功能模块清单`
  - `模型定义`
  - `接口定义`

#### 5. 全量重写策略

* 若某个模块在多轮修复后仍未达到预期效果，可考虑对该模块所在文件进行**功能性重写**，而非仅做局部修复。

#### 6. 使用 Yarn 管理依赖

* 项目依赖必须通过 `Yarn` 管理。
* 禁止混用 `npm` 或其他包管理工具。


## 代码规范

1. **遵循代码规范**：所有代码必须符合技术栈规范。

2. **保持风格一致**：修复错误时保持与现有代码风格一致。

3. **特殊字符处理**：生成代码及修复错误时注意HTML特殊字符，避免错误地使用`&lt;`代替`<`，`&gt;`代替`>`。

## 命名规范

### 1. 模块命名格式

| 模块级别 | 命名格式           | 示例                   | 文件/路径使用 |
| ---- | -------------- | -------------------- | ------- |
| 项目名  | 英文，首字母小写       | `demoPartner`        | 使用英文名   |
| 业务模块 | 中文名称 + 英文名（名词） | 产品管理 (Product)       | 只使用全小写英文   |
| 功能模块 | 中文 + 英文（名词+动词） | 产品新增 (ProductCreate) | 只使用全小写小写英文   |

> 文件名与路径使用全小写英文名

### 2. 命名一致性

* 所有代码中，同一模块名称必须完全一致。
* 系统应支持自动校验名称一致性，防止拼写差异。
