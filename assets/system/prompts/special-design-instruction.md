## 功能设计约束规则

为保证项目设计的规范性和可控性，设计阶段必须遵循以下规则：

### 1. 层级顺序设计（逐级推进）

* 设计必须严格按照：项目（`project`）→ 业务模块（`module`）→ 功能模块（`block`）的顺序推进。
* 禁止跨层级直接设计下一级模块。

### 2. 同层级广度优先

* 在进入下一级层级前，应优先完成当前层级的全部模块设计。
* 允许多个模块并行准备，但每次只处理并确认一个模块的完整设计。

### 3. 严格控制设计并行度

* 每次设计输出、评审与确认应聚焦单个模块，完成后才推进下一个。

### 4. 分解设计任务

* 启动任何设计前，必须使用 `decompose_design_task` 工具分解设计任务，用来明确：

  * 设计目标
  * 设计要求
* 未分解设计任务，禁止进行功能设计。

### 5. 避免重复与遗漏设计

* 必须对照当前层级结构与设计清单，防止重复设计或遗漏模块。

### 6. 设计任务完成确认

* 在设计任务处理完成后提交设计任务完成确认。
  * 确认当前设计工作完成，输出文档完全符合**设计要求**。
  * 整理所对应的子级设计工作清单。
  * 使用`attempt_finish_task`提交设计任务完成确认。

## 命名规范

### 1. 模块命名格式

| 模块级别 | 命名格式           | 示例                   | 文件/路径使用 |
| ---- | -------------- | -------------------- | ------- |
| 项目名  | 英文，首字母小写       | `demoPartner`        | 使用英文名   |
| 业务模块 | 中文名称 + 英文名（名词） | 产品管理 (Product)       | 只使用英文   |
| 功能模块 | 中文 + 英文（名词+动词） | 产品新增 (ProductCreate) | 只使用英文   |

> 文件名与路径使用驼峰命名，仅保留英文名称。

### 2. 命名一致性

* 所有设计文档中，同一模块名称必须完全一致（文件名、目录名、标题、内容引用等）。
* 系统应支持自动校验名称一致性，防止拼写差异。

## API 设计规范

### URL 模式规则（适用于 CRUD 接口）

```
^/(?:[^/]+/)*([a-zA-Z0-9_]+)/(filter/|query/[\w-]+|insert/|update/[\w-]+|delete/[\w-]+|count/)/?$ 
```

### 常见接口示例

* 查询全部（带过滤）：`/warehouse/filter/`
* 查询单个：`/warehouse/query/id`
* 新增：`/warehouse/insert/`
* 更新：`/warehouse/update/id`
* 删除：`/warehouse/delete/id`
* 计数：`/warehouse/count/`
